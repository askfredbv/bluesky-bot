# Retro: six weeks of building infrastructure on a broken bot

**Date:** 2026-05-08
**Versions covered:** v4.14 → v4.18.0 (approximately 2026-04-14 → 2026-05-08)
**Trigger:** User pulled up the live Bluesky feed, found five days of bad posts, and asked why none of the sessions in between had caught it.

---

## TL;DR

For six weeks, every session added infrastructure (telemetry, voice rules, dedup machinery, audit scripts, log guards, bio polish, release discipline) to a bot whose primary failure mode — shipping `"Notes on {topic} — more soon."` placeholder posts when the model chain exhausted — was hardcoded into `src/agents.py` and never surfaced. The bot has 26 followers and produced 4 likes / 2 replies / 0 reposts in the week ending 2026-05-08. Half the posts had zero engagement of any kind. The user caught the pattern by looking at the feed. The fix took 30 minutes once we looked.

Do not let this happen again. The corrective is the easiest possible discipline: **before reasoning about post quality, pull the last 10 posts from the public API and read them.** Metrics about the feed are not a substitute for reading the feed.

---

## What actually happened

### The bug

`src/agents.py` had this since at least v4.14:

```python
fallback_post = f"Notes on {topic} — more soon."
# ... rescue loop iterating models, retrying, eventually exhausting ...
return [fallback_post[:MAX_POST_LENGTH_BSKY]], topic
```

When the model priority chain exhausted (which happened on at least 3 of the 6 most recent runs), `generate_content` returned this hardcoded string instead of a real post. The return path bypassed `_apply_voice_trim` entirely, so every voice rule the project had shipped — `BANNED_HYPE_WORDS`, `BANNED_QUESTION_PATTERNS`, `BANNED_OPENERS`, the v4.17.1 `BANNED_TEASER_PATTERNS` — was inoperative on this code path.

The bot was shipping zero-content placeholder posts that promised continuations it had no machinery to deliver, on most of its bad days, for at least six weeks.

### Why the chain exhausted

`filter_available_models()` runs at startup and prunes the priority list against what the Gemini API says is available. On every recent run it removed:

```
gemini-1.5-flash-latest, gemma-3-27b-it
```

Leaving `[gemini-2.5-flash, gemini-2.0-flash]`. Of those, `gemini-2.0-flash` consistently returned `ClientError` (model_unavailable), and `gemini-2.5-flash` hit `JSONDecodeError` on roughly a third of attempts. Two attempts on 2.5-flash + one bounce off 2.0-flash = chain exhausted = fallback fires.

So the bot was effectively running on a single working model, with a 30%+ JSON-failure rate on the primary, with a hardcoded garbage-output fallback when the chain ran dry.

## What we built in those six weeks

Roughly in order:

- **v4.14** — four voice ban lists, defensive trim helpers
- **v4.15.x** — post-length hard enforcement, broadcast invariant violations, runtime-state cooldown helpers
- **v4.16** — Phase 1 Steps 1–3b (retry helpers, feed_health, BroadcastResult, per-thread retry budgets), Phase 4a recon script, dedup machinery (`recent_mode_topics`, recent-post-excerpt avoidance), SafeLogger reserved-key guard, bio rewrite + cleanup of half-implemented bio-update infrastructure, branch cleanup (42 stale branches), three plan-doc files deleted, ~1000 lines of dead code weeded
- **v4.17.0** — Phase 1 Steps 4 + 5 (post_metrics + feed_health refresh/prune), production-confirmed
- **v4.17.1** — `BANNED_TEASER_PATTERNS` ("more soon" / "stay tuned" / 🧵), Track A formatting features in post_metrics, Imagen diagnostic surface, audit-script Mastodon preflight
- **v4.18.0** — killed the catastrophic fallback, Imagen 3 → Imagen 4

Every commit was technically sound. Every test passed. The release notes are clean. The code is more maintainable than it was six weeks ago. **And it did not move the goal a single millimetre** until the user forced the issue and we removed twelve lines of placeholder generation.

## What we missed

### The diagnosis-lag pattern

Three separate bugs in this six-week window hid behind the same shape: a generic exception type logged without the message body.

1. **2026-04-25 → 2026-04-29 (Step 2 KeyError, ~4 days):** `feed_health_record_failed` logged `error_type=KeyError` with no message. We spent multiple sessions reading code, hypothesising, scheduling a diagnostic patch, waiting for the next Curator run. Once `error_msg=str(e)[:200]` was added, the actual error — `"Attempt to overwrite 'filename' in LogRecord"` — surfaced in one run and the fix was one line.

2. **2026-05-03 → 2026-05-08 (Imagen 3 deprecation, ~5 days):** `image_generation_failed` logged `error_type=ClientError` with no message. Image generation had been silently failing for weeks. Once the same diagnostic discipline (`error_msg=str(exc)[:200]`) was applied on 2026-05-05, the actual error — `"404 NOT_FOUND. models/imagen-3.0-generate-002 is not found for API version v1beta"` — surfaced on the next run and the fix was a config-line change.

3. **2026-04-14 → 2026-05-08 (the hardcoded fallback, ~6 weeks):** No log event at all. The bot shipped placeholder posts and the runs were `conclusion: success`. The only diagnostic was the live feed — and nobody opened it.

**The pattern:** `error_type` alone is rarely enough to act on. **`error_msg=str(e)[:200]` on every except that logs is now the project default**, written into the project memory file. Three different bugs surfaced the same way; the discipline pays for itself within a week of shipping.

### The infrastructure-over-output trap

The plan we were executing — `PLAN_engagement.md` — was designed to do four things in sequence:

1. Capture metrics (Phase 1)
2. Surface them in a digest (Phase 2)
3. Act on signals (Phase 3)
4. Participate via proactive replies (Phase 4)

The plan is well-reasoned. The phases are appropriately gated. The non-goals (no engagement-chasing voice changes, no per-platform divergence) are sound.

But the plan assumes an audience exists to engage with the content. We had 26 followers. The plan's success criteria (Phase 2 digest with 2+ weeks of data, Phase 3 scoring multipliers with 4+ weeks of data) require **engagement data**, which requires an audience, which the plan never builds. Phase 4 (proactive replies) is the only path in the plan that creates discovery — and it was gated on "Phase 1 producing data to inform reply-prompt design," a gate that was always conservative-by-default.

We optimised the writing for readers who didn't exist. The right order was almost certainly:

1. **Get discovered** (Phase 4-style: proactive replies, custom feeds, hashtag strategy)
2. **Once an audience exists, measure** (Phase 1, which we have)
3. **Tune what works** (Phase 2 / Phase 3)

We did 2 before 1. The telemetry is gorgeous and the audience to apply it to is twenty-six people who mostly don't engage.

### The metrics-as-substitute-for-reading trap

I (the AI agent) checked Actions logs constantly. I read `gh run view` output. I grepped for failure events. I monitored test counts. I cared about acceptance gates and run conclusions.

I never once opened `https://bsky.app/profile/askfred.be` until the user instructed me to.

This is the deepest lesson. Telemetry tells you what events fired, not whether the output was good. A run that ships `"Notes on Career — more soon."` exits with `conclusion: success` because nothing in the pipeline raised. The telemetry I built was incapable of detecting the bug it was meant to help diagnose, because the bug was *what got shipped*, not *what happened in the pipeline*.

The corrective is trivial: pull the last N posts and read them, at the start of every session that touches the bot. Pulling via `app.bsky.feed.getAuthorFeed` takes 5 seconds. Reading 10 posts takes a minute. The bug we spent six weeks not finding was obvious in 30 seconds the moment I did it.

## What changes going forward

### Hard rules

1. **Read the live feed before reasoning about post quality.** Project memory file (`project_bluesky_bot.md`) has this as the "hardest-earned lesson" line. Treat it as binding for every session.

2. **`error_msg=str(e)[:200]` on every except that logs.** Three diagnosis-lag bugs is enough. Logging `error_type` without `error_msg` is now a bug to fix on sight.

3. **Hardcoded fallback strings are forbidden.** Any fallback that produces user-visible output must go through the same voice trim / validation path as model-generated output. When that's not possible, **skip the operation entirely** rather than ship a placeholder. Same philosophy as `broadcast_invariant_violated` from v4.15.3.

### Soft rules

4. **Question the plan's phase ordering when an early phase isn't producing visible results.** Phase 2 needs an audience; Phase 4 builds an audience; running 1 → 2 → 3 → 4 assumed the audience would arrive on its own. It didn't.

5. **Padded "wait for next session" framings are a smell.** The user calibrated me on this on 2026-05-05 (`"I'd rather fix stuff fast"`). Most of the "wait" recommendations I gave in the six weeks were ship-now items dressed up as discipline. Defaults: bounded + brand-safe + has-a-natural-validator → ship now. Real wait gates: production validation, data accumulation, brand decisions, unverified base. Memorise the distinction.

6. **Production-confirmed acceptance is not the same as user-confirmed value.** A run can exit `success`, all telemetry events can be clean, all tests can pass, and the bot can still be shipping garbage. Acceptance criteria for any output-shaping change should include reading the actual output, not just the run log.

### Concrete project actions remaining

- User manually removes the placeholder posts from Bluesky and Mastodon profiles.
- Decide explicitly whether the goal is "build a following" (active acquisition work needed; Phase 4b becomes immediately actionable) or "have a representation account" (v4.18.0 is approximately done; declare project mature, maintenance-mode).
- If the goal stays "build a following," the implicit gating that kept Phase 4b waiting for six weeks is the next thing to question.

## A note to future agents reading this

If you are starting a session on this project and you have not yet read the live feed at `https://bsky.app/profile/askfred.be`, **stop and read it first**. The lesson of this retro is not abstract; it is structural. The infrastructure in this repo is good. The plan is sound. The voice rules are tight. None of that helped because nobody looked at what was actually shipping.

The user is patient. They were patient through six weeks of sessions that built around the central failure mode without catching it. Do not assume that patience is unlimited or that the absence of complaint means things are working. Verify the output.
